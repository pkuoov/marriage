## 优先处理

- [x] R01 · P1 · 模型验证：旧文案仍能从材料追问和已删除的探问返回。

  [savedContentRefresh.js](/Users/pkuiloveoov/code/love/src/runtime/savedContentRefresh.js) 已刷新主要问答和材料选择反馈，但没有重建 `caseOvernights.documentEarnedQuestions`。第二夜对账页直接播放这个存档字段，而不是重新读取新版文档问答。构造存档经完整 `refreshSavedCaseContent` 后，活动材料问题仍是旧问题、旧回答。

  另一个漏口是正在播放的 `reviewProbes`：如果探问已删除，刷新时找不到新的 probe，原来的 `sceneQuestionFocus.pick` 会被保留。普通问答刷新只查 `casualQuestions`，也未覆盖运行时允许的 `dialogueOptions` 和派生问答。

  后续做法：迁移所有当前可播放的快照；删除的活动问题应退回合适的当前入口，不继续播放旧答案。对已回答问题保留完成状态，避免刷新正文后再次扣费或重复询问。历史案卷单独处理。

- [x] R02 · P1 · 模型验证：删题或重排后，旧选择可能变成另一道题。

  同一刷新文件先匹配问题文字或 `suspicionLabel`，匹配失败便回退到 `optionIndex`；材料选择则直接按索引取新版选项。构造「原题被删、另一题占据原索引」的状态后，玩家保存的提问被替换成了另一问；材料选择也随新顺序换了含义。场景与材料题本身的记录键还含位置索引，后续挪动整场时风险更大。

  后续做法：给场景、问题和材料选项使用稳定身份，并为撤题或合并题写明确迁移关系。无法可靠匹配时，不替玩家选择另一项。补验要包括删除、插入和重排，不能只验证同一位置换了一句话。

- [x] R03 · P1 · 代码风险，需核对显示与结算：新回答可能搭配旧处罚、旧路线评价。

  之前把一些错问改成有效提问，刷新会更新问答的 `correct` 和文案，同时保留已发生的预算、动作日志和路线历史。保留玩家历史有必要，但如果新界面显示「有效提问」，案卷或收尾仍从旧快照称其为偏题、算成旧路线，玩家会看到相互矛盾的评价。增加或删去关键问题也可能影响完成数量与结算分母。

  后续做法：明确已完成选择按哪个版本结算，区分正在播放的新内容和旧版本历史。不可为消除显示矛盾就一律补耐心、重算成绩或清空进度。拿第一案共同花销问法及账单唯一关键点做旧档对照，检查回答、关键标记、剩余次数、回顾和最终路线是否自洽。

- [x] R04 · P1 · 已验证展示路径：材料卡还会把作者评语当成原件说明。

  [materialRecordView.js](/Users/pkuiloveoov/code/love/src/ui/materialRecordView.js) 仍显示收到卡片的 `detail`。第一案 `daily-credit-anniversary.detail` 是「体面不是单向投喂，她也把它发给了观众看」。用该段已完成的状态生成材料列表和 HTML，确实包含这句，结果见 [material-probe.html](/Users/pkuiloveoov/code/love/output/post-edit-risk-review-2026-09-12/material-probe.html)。

  这解释了为什么对白已经删改，旁边材料中仍会出现同类 AI 文案。后续还需核对卡片正文里的消费分类、人物动机是否确由当前已取得材料支持。

  后续做法：逐卡区分原文、必要出处说明和作者解释；材料入口保留前两者。不要整批删除 `detail`，其中也有必要的材料范围说明。示意图若烧入旧文字或旧金额，需要与正文同步核对。

## 下一轮改稿和试玩需要防住

- [x] R05 · P2 · 源码存在，具体触发待查：字段缺失时又回退到套话，校验可能继续诱导凑句子。

  [sceneQuestions.js](/Users/pkuiloveoov/code/love/src/ui/sceneQuestions.js) 可以从其他选项派生普通问答，并自动生成「钱这块当时怎么说的」等问句；[app.js](/Users/pkuiloveoov/code/love/src/app.js:1347) 还留有「如果把情绪先放一边……谁要承担成本」的深问兜底。当前主包不一定走这些路径，但删字段、每日生成或备用入口可能重新触发。

  [dialogueTexture.js](/Users/pkuiloveoov/code/love/src/runtime/dialogueTexture.js) 仍有最低短回答数、长回答数、打断标记数等质量指标。它们不直接生成对白，却可能再次让改稿为了过检查而加停顿、争辩和自我解释。不能把所有指标都判成错误；应确认它们有没有压过具体场景需要。

  后续做法：检查主包之外的生成与备用入口，确认删去的功能不会靠默认文案偷偷补回来。文案门禁侧重前提、出处和接话，不以凑够同类句型替代人工判断。

- [x] R06 · P1 · 待输入实测：长按确认键可能从推进对白变成误选关键项。

  [app.js 的键盘处理](/Users/pkuiloveoov/code/love/src/app.js:210) 对确认键没有过滤 `event.repeat`；[focusInputControl.js](/Users/pkuiloveoov/code/love/src/ui/focusInputControl.js:204) 会先推进对白，没有对白时激活当前或默认按钮。新增明显的关键按钮、调整焦点布局后，需要确认按住空格或 Enter 时不会越过对白末尾，自动选中下一屏的第一项。手柄有按下沿判断，不能用手柄通过代替键盘补验。

  后续做法：长按跨越「对白末尾、关键选择、正式出示」三种边界，验证必须松开再确认。另测快速双击和触屏滚动选项；Esc 关闭材料后应回到原焦点，不能推进剧情或意外选择。

- [ ] R07 · P2 · 资源风险，未做听看复现：新台词仍可能配旧声音、旧人物或旧情绪。

  场景通过 `audioCueId` 引用独立的语音目录和录制清单。当前检查会核对目录与录制清单的 transcript 是否相等，但这不能普遍证明引用它的场景仍在讲同一件事。例如彩礼白天表姐门口还挂着 `voice.case3.dinner-pause`，目录里的文本却是饭局上问本科；该语音目前是 `planned`，不能据此声称玩家现在已经听到错音，但将来启用资源时会暴露错配。

  此前把问题从挑衅改为正常核实、把说话人从律师改为主播后，也需核对姿态、名牌、表情和情绪音效；仅替换台词字符串不会自动修正这些映射。职场主管录音与同事 profile 的具体问题已在主清单 W05 登记，不重复计数。

  后续做法：先对照实际场景核映射和录音脚本，确认当前发声者与画面一致，再补录或补画。只有材料和对白确有新发现时才使用强烈命中反应，不让普通核实也统一表现成心虚、认罪或震惊。
