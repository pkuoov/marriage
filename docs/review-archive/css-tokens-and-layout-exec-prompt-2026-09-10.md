# 单 A｜把已有令牌真正用起来（631 处）

## 现状

`:root` 有 17 个令牌（[00-foundation-and-title.css:1](src/styles/00-foundation-and-title.css#L1)），但全仓库：

```
硬编码 rgba()/hex : 1642 处
var(--...) 引用   :  110 处      ← 15 : 1
```

其中 **631 处的 RGB 值和已有令牌完全一致**，却写成了字面量：

| 出现次数 | 字面量 | 对应令牌 |
| --- | --- | --- |
| **302** | `rgb(237, 241, 238)` | `--ink` |
| **236** | `rgb(101, 214, 194)` | `--accent` |
| **53** | `rgb(212, 180, 106)` | `--gold` |
| 19 | `rgb(121, 184, 204)` | `--cyan` |
| 18 | `rgb(13, 16, 13)` | `--night` |
| 2 | `rgb(17, 20, 16)` | `--paper` |
| 1 | `rgb(177, 106, 115)` | `--rose` |

现在想调一次主色，要改 236 处。

## ⚠️ 必读：直接替换会静默失效

**这 631 处几乎全部是 `rgba()` 带 alpha 的形态，且 alpha 有 60 种不同取值**（`.018` 到 `.94`）。

而现有令牌存的是 **hex**（`--accent: #65d6c2`）。所以：

```css
/* ✗ 错误：CSS 不接受，整条声明被丢弃，元素直接失去该颜色 */
border-color: rgba(var(--accent), .12);
```

**这类错误通常不会抛 JS 异常**；变量展开后值无效时，属性可能回到初始值或继承值，不能假定会回退到前一条声明。**不要用这种写法。**

## 正确改法：加通道三元组令牌

在 `:root` 里为这 7 个令牌**各加一个 `-rgb` 通道版本**，与现有 hex 令牌**并存**（不要删 hex 版，还有 110 处在用）：

```css
:root {
  --ink: #edf1ee;
  --ink-rgb: 237, 241, 238;        /* 新增 */
  --accent: #65d6c2;
  --accent-rgb: 101, 214, 194;     /* 新增 */
  --gold: #d4b46a;
  --gold-rgb: 212, 180, 106;       /* 新增 */
  --cyan-rgb: 121, 184, 204;
  --night-rgb: 13, 16, 13;
  --paper-rgb: 17, 20, 16;
  --rose-rgb: 177, 106, 115;
  /* 其余不动 */
}
```

然后机械替换，**alpha 原样保留一个字符都不改**：

```css
rgba(101, 214, 194, .12)   →   rgba(var(--accent-rgb), .12)
rgba(237, 241, 238, 0.10)  →   rgba(var(--ink-rgb), 0.10)
```

裸 hex（`#65d6c2` 等）的使用处可替换为 `var(--accent)`。**必须跳过令牌自身定义**，否则 `--accent: var(--accent)` 会形成循环引用并使变量无效。若存在局部主题覆盖，还须检查该作用域的 token 实际值，不能默认与原字面量等价。

**注意空格变体**：存在 `rgba(101,214,194,...)` 无空格写法（3 处）和 `rgba(101, 214, 194, ...)` 有空格写法（233 处），两种都要覆盖。建议用正则按 `rgba?\(\s*101\s*,\s*214\s*,\s*194\s*,` 匹配，不要用朴素字符串替换。

## 边界

- **只替换上表这 7 个精确 RGB 值**。其它颜色一律不动。
- **alpha 值一个都不许改**（包括 `.10` 不要规范化成 `.1`）。`.10` 与 `.1` 数值等价，本身不会造成视觉变化；保留原拼写是为了控制 diff，并不是 CSS 语义要求。
- 不要顺手合并"看起来差不多"的颜色（见下面的调色板漂移报告）。

## 顺带报告（本轮不改，只列进交付）

# 单 B｜竖屏舞台填充（已修复）

## 复核后的根因

原单只追到 `10-live-stage-shell.css` 的 680px 下限，遗漏后续覆盖。当前序章使用 `display: block`，对白为绝对定位；调整旧 grid 的 `1fr` 不会改变对白布局。

实际生效的是 `80-live-console-and-interludes.css` 中移动端 `[data-live-stage]` 的 `min-height: max(600px, calc(100svh - 13.5rem))`。扣除的固定高度与真实顶栏高度不一致，外层也没有补足剩余空间。`.live-console-shell` 的 `align-items: start` 又会阻止舞台随外层一起拉伸。

本轮在末尾 `95-visual-polish.css` 加窄屏专用规则：让含对白舞台的 main 以 100dvh 为最小高度（100svh 回退），顶栏使用实际高度，story-grid 占剩余空间，舞台 `align-self: stretch`。不修改桌面布局，不改变对白框高度。

保留 `.cafe-prologue-step-1` 材料桌的紧凑特例。长内容允许正常滚动，不通过固定高度或隐藏溢出来伪造“没有黑边”。

## 基线

以下为同一测试状态、序章第一句、即时文字的实际测量。旧单手机 155px 的数据已不适用于当前换行后的顶栏。

| 视口 | 修改前 app 底部留白 | 修改后 | 说明 |
| --- | --- | --- | --- |
| 1440×900 | 19.30px | 19.30px | 舞台及对白矩形保持 |
| 1024×768 | 19.30px | 19.30px | 舞台及对白矩形保持 |
| 768×1024 | 155px | 0px | 舞台底边为 1024px |
| 390×844 | 116.50px | 0px | 舞台底边为 844px；按钮底边为 835px |

不能只设 `#app { min-height: 100dvh }` 后测 app 底部：这样可能只是把空白移进容器，舞台仍未长大。

## 材料桌补验发现（已修复）

手机单列规则没有重置旧按钮的第二列定位，材料区被挤到约 109px，内部两张卡继续并排，文字近乎竖排。已在窄屏限定范围内重置操作按钮列定位、材料卡改为一列，并让紧凑材料桌正常展开。材料板恢复约 338px，卡片约 310px；实际完成了聊天截图的选择和出示，进入妻子回应。该问题来自既有规则冲突，不是 680px 舞台下限。
