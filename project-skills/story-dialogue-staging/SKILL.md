# Story Dialogue Staging

把“剧情想法”改造成能在游戏里成立的整晚故事、逐幕分镜和可玩台词。严格按以下顺序工作：**完整剧情 → NPC角色网 → 逐幕分镜 → 连续对白 → 运行时字段 → 实际回放**。

## 与其他项目技能的分工

开始前完整读取：

- `project-skills/case-scriptwriting/SKILL.md`：负责单案证据账本、疑点与问题点、口语化和材料公平性。
- `project-skills/detective-plot-coupling-review/SKILL.md`：负责 A/B 故事、假解、反转、未知边界和承诺账本。
- 涉及运行时、UI或可玩流程时，再读 `project-skills/livestream-game-flow-review/SKILL.md`。

本技能负责三者之间最容易断掉的部分：整晚故事是否完整、NPC是否真正参与、场景是否变化、白天行动是否改变第二夜、台词是否按信息状态接力。

## 工作顺序

### 1. 先核对现状，不立刻改台词

读取目标案、相邻案件、包级QA、现有设计稿和相关运行时。先记录：

- 当前故事从哪一夜开始、在哪里挂断、何时回拨。
- 来电人、主播和NPC分别知道什么。
- 哪些文件已有用户改动；保留无关改动。
- 当前NPC是主动出现、被玩家求助，还是只作为提示按钮存在。
- 当前场景是否真的换了背景、HUD和交互，还是只换了一段说明文字。

如果现有内容只有字段堆叠，没有完整故事，先停下字段修补，回到第2步。

### 2. 先写一版不带UI字段的完整剧情

用连续叙事写清：

1. 第一夜来电为什么发生在今晚。
2. 来电人的初始版本和自我修剪。
3. 哪个具体问题迫使连线中断。
4. 主播或NPC为什么在收播后采取行动。
5. 第二天去哪里、找谁、做什么，而不是“获得一条提示”。
6. 白天行动新增什么证据可能，也暴露什么盲区。
7. 第二夜如何从白天结果开场。
8. 来电人修正哪句证言、承认什么代价。
9. 今晚能确认什么，仍不能确认什么。
10. 主播做了什么负责的行动，而不是只说“证据不足”。

完整剧情没有成立前，不写 `sceneVersions`、按钮文案或分支字段。

### 3. 设计NPC角色网

每个主要NPC必须拥有以下六项：

- **欲望**：此刻为什么愿意参与。
- **方法**：只能从哪类材料或语言入手。
- **偏见**：容易过度相信什么。
- **拒绝**：明确不肯替玩家判断什么。
- **场景**：固定地点、正在做的事、可见物件。
- **后果**：玩家找TA后，第二夜具体改变什么。

NPC不是答案机。至少满足一项戏剧动作：拒绝、打断、误读、护短、要求玩家二选一、与另一NPC冲突。

场下求助 NPC 是轻量例外，不冒充主要剧情 NPC：

- 只在玩家主动点击求助后出现，不能自动插话。
- 只复述当前屏幕已有事实之间应比较的方向，不新增材料、不报答案、不替主播发问。
- 不解锁选项、不改变路线分或听众耐心、不进入专业顾问委托。
- 必须有独立角色卡、稳定口吻和知识边界；提示接口的人格化不等于新增一条案件信息源。

本试玩版沿用以下出场结构，除非用户明确改主线：

- 一个NPC在听完直播后主动联系主播，只纠正行动方式，不提供案件答案。
- 两个NPC由玩家在不同案件的第二天主动前往求助，必须进入不同真实地点。
- 最终案让主要NPC共同出场并公开冲突；他们分别只看见一部分。

### 4. 建立跨夜因果表

每个跨夜案件至少写出：

| 节点 | 必须回答 |
| --- | --- |
| 第一夜挂断锚点 | 哪个未解决的具体名词、数字、账户或列名迫使挂断？ |
| 白天机会成本 | 玩家能做几件事，为什么不能全做？ |
| NPC地点动作 | 玩家在场景里排列、比较、核对、追问或选择什么？ |
| NPC边界 | NPC确认什么，又拒绝确认什么？ |
| 带回物 | 使用玩家看得懂的名称，不暴露内部ID。 |
| 第二夜开场 | 每种带回物分别改变主播第一问和来电人第一句什么？ |
| 收麦未知 | 哪个有形问题仍留在麦外？ |

白天选择如果只奖励一段说明文字，视为失败。它必须改变第二夜的开场、可见材料、来电人防备或可选行动。

### 5. 再拆逐幕分镜

每幕写明：

- 时间与地点。
- 出场人物及其当下欲望。
- 画面中的物件或动作。
- 本幕新增的一项事实或压力。
- 玩家动作。
- 信息状态改变。
- 退出钩子。
- 预计时长。

一幕只承担一个主要变化。不要靠加长气泡制造时长；依靠场景、材料和动作种类制造体量。

### 6. 写连续对白，再拆字段

先写从开场到收麦的连续对话稿，再拆进JSON。逐轮检查：

- 每句接住上一句的词、问题或回避。
- 主播只能问已经在屏幕上出现的事实。
- 来电人报告看见、听见、做过什么，不代替玩家推理。
- 来电人回忆带情绪和自我辩护，不做案情摘要。
- NPC说法体现欲望和偏见；删掉任何人都能说的“功能台词”。
- 关键气泡原则上不超过90个汉字；长句拆成动作或下一轮。
- 同一个物件保持同一称呼，除非改称本身是剧情变化。
- 外围问题也必须是主播真的可能问的问题。
- 最终未知不能被顾问、弹幕、复盘或分享文案偷偷闭合。

每个回拨开场都检查与下一段正文是否重复。动态开场负责提出问题，正文负责回答或回避，不要连续复述同一句事实。

### 7. 场景切换必须完整

当玩家“去找NPC”时，至少同步改变：

- 背景或场景类名。
- 场景标题和时间。
- 直播HUD、`ON AIR`、听众耐心等直播元素退出。
- 交互动作从直播选择变为地点内动作。
- 环境物件和NPC正在做的事进入正文。
- 完成动作后能返回调查台或地图。

仅在直播框里显示“你去了某地”的文本，不算场景切换。

### 8. 运行时落地同步更新

剧情改动后同时检查：

- `truthBoundary`、自我修剪、最终未知。
- A/B故事与承诺账本。
- 回拨开场、收麦选择、复盘和分享文案。
- NPC行动ID、携带物、选择门控和显示名称。
- QA报告中的NPC与跨夜契约。
- 新场景背景和缓存版本。
- 生成内容索引。

任何会直接显示给玩家的ID必须可读。不要让 `timeline-clarity`、`window-seat-proof` 一类内部名出现在选择按钮或携带物列表。

### 9. 把“结案、案间、新案”拆成三件事

相邻案件不得从回看页直接跳到下一通直播。采用固定顺序：

`收麦回看 → 案件结案 → 广告间隙 → 下一案标题 → 新案直播`

- **案件结案**不是证据清单。必须依次给出：来电提出了什么、麦上问到了什么、离台核实改变了什么、今晚能确认什么、今晚不能替人定什么、节目建议的下一步。
- `能确认 / 仍无法确认`必须是陈述式证据状态，例如“尾号 3301 的账户归属仍无法确认”；不要把“尾号 3301 是谁的账户？”这类调查问题当作结论展示。
- **广告间隙**只承担节奏和下一案物件钩子。不要再复述上一案结论、玩家路线或后台命中情况。
- **下一案标题**必须明确案号、案件名和本案唯一核心问题，再进入直播。它是正式开篇，不是目录页；若用户要求显示案名，此规则优先于“隐藏案名”的旧约束。
- 案件结案内容进入数据包字段（如 `caseClosing`），下一案标题进入数据包字段（如 `caseTitle`）；不要在 `app.js` 按 `plotId` 写特判文案。

### 10. 玩家可见文案：只说人、物和已发生的事

所有台词、复盘、提示和按钮按以下规则过一遍：

- 指明说话者和信息来源。短信、运营通知、律师留言、主播自白不能混成无主旁白。
- 角色说话只报告眼前的物件、数字、动作和自己的决定；不要替玩家总结“钱流结构线”“把缺口钉住”“这已经不是原来的意思”一类抽象推理。
- 复盘若有新材料，直接说材料是什么及其可确认范围；不要拼接“你刚才一直……”或“后台补来的那页又……”等系统旁白。
- 主播统一使用设定名和身份（当前为林旭阳），不要在玩家可见对话框里用第二人称“你”代替主播。
- 一句台词若可由任何NPC或旁白说出，补进人物立场、正在做的动作或具体材料；仍无差异就删掉。
- 未知项保持未知。顾问、弹幕、结案页、分享文案都不能以语气把未确认账户、身份、动机或还款能力说成已定事实。

### 11. 叙事UI要服务阅读，不替玩家推理

当内容变长或可选项变多时，先改信息层级，再加文字：

- 一个节点有多个可问问题时，使用二级菜单：先显示当前对话与“提问”，再弹出同级问题格；问完一项返回菜单，已问项禁用。不要把所有问答和回答堆在同一屏。
- 选择数原则上不超过四个，使用等权的四方格或双列卡；不要用颜色、顺序或“关键/推荐”泄露正确答案。
- 部分节点可以只让玩家选择疑点方向：按钮显示 `suspicionLabel`，选中后由林旭阳说出对应 `question`。同一节点要么全部显示疑点方向，要么全部显示完整问句；不能只给正确项短标签。
- 时间排序要分为“已放入的编号槽位”和“待放的时间点”，并提供明确的清空与确认；不要把所有词条塞进一行。
- 社交平台、朋友圈、聊天记录等材料须以对应产品形态呈现：头像、时间、图片、文案、评论或删除痕迹。不要把截图证据退化成干巴巴的文字段落。
- 场景切换后，旧场景的直播HUD与操作不应残留；标题、时间、背景、可点物和人物动作必须共同改变。
- 像素风过场只放在开麦、挂断、昼夜转换、回拨、案间等大切点；保持短促、不可操作、尊重 `prefers-reduced-motion`，不要在每次对白刷新时重复播放。
- 连线内每两到三个问答至少要出现可见的视觉状态变化：背景取景或色调、道具位置、来电人姿态/表情提示至少改变一项。不要只替换气泡文字。
- 立绘差分只有在资源真实存在时才能引用；没有差分图时，用同一张图的姿态、取景、明暗和表情提示做状态变化，不要反复请求不存在的 `*_guarded.png`、`*_pause.png` 后再静默回退。
- 从写实立绘转像素风时先做单案、同一角色的 `neutral / guarded / pause` 三态样张并在真实 UI 尺寸验收；未验收前保留现有资源回退，不批量套像素滤镜，也不混用写实脸与像素差分。

#### 匿名来电人立绘基线（2026-07-18 复审定稿）

以后生成、重画或验收四案来电人立绘，统一遵守：

- 使用暖色可读的三分之二侧脸，人物不直视镜头；匿名感来自观看角度和五官信息简化，不来自遮脸。
- 眼睛只保留简化像素形，不画细瞳孔、强高光、睫毛等身份化细节。
- 禁止常驻眼部光带、发光面罩、墨镜、黑色遮罩和上半脸重阴影；禁止为了匿名把人物压成审讯、恐怖或赛博气氛。
- `neutral / guarded / pause` 必须是同一个人、同一服装、同一道具、同一身材和同一基线。`guarded` 靠肩颈收紧、抱臂或把物件抱紧；`pause` 靠手机短暂离耳、视线下移或肩膀放松，不靠换脸或变暗。
- 信号断帧、扫描线和像素错位只用于接通、断线等瞬间过场，不常驻脸部或全身立绘。
- 每案以旧立绘锁定身份、服装和道具，以案 1 暖色侧脸样张锁定面部光色与像素密度；同案三态优先一次生成在同一张等栏母表，减少身份漂移。
- 透明图使用平坦绿幕去背并检查 alpha、透明四角和绿边；交付 `256×512` 真透明母版，再以最近邻放大为 `1024×2048` 发运版，禁止平滑插值。
- 替换运行时资产后同步提升 manifest 查询版本、重建内容索引与三份台本文档，并在 `390×844`、`1366×768` 和 Steam Deck 尺寸检查对白遮挡、人物亮度与三态辨认。

详细 prompt、目录与验收门以 [pixel-art-transition-and-portrait-direction.md](../../docs/pixel-art-transition-and-portrait-direction.md) 为准。旧文档里“半剪影／眼部光带”段落只作历史记录，不得再作为生成要求。

### 12. 为交界面专门回放

新增或修改结案、案间、标题、菜单、排序或材料展示时，浏览器回放必须额外断言：

1. 回看末页先进入 `caseClosure`，不是直接进入下一案。
2. 结案页同时出现流程、确认边界、未定边界和下一步。
3. 点击案间后只显示节目间隙与下一案物件。
4. 下一案先出现案号、案名、核心问题，点击后才进入 `caseOpen`。
5. 长问答能打开菜单、作答、返回菜单；材料与排序在窄屏没有重叠或截断。
6. 连续问答至少采样两个回合，断言 `.visual-scene` 与 `.case-portrait` 的状态类各出现过两种以上；不能只检查立绘节点存在。

将这些断言写入 `scripts/verify-logic.js` 或 `scripts/smoke-browser-replay.js`。不要只靠源码检索判断UI流程成立。

## 常见失败模式

- **先拆字段再补故事**：各字段单独好看，但人物动机和信息顺序断裂。
- **NPC换皮提示器**：NPC看一眼材料就说出正确答案。
- **假场景切换**：换了文字，没有换背景、HUD和交互。
- **白天不影响夜晚**：不管玩家去了哪里，回拨台词完全一样。
- **专家门控道德答案**：见过某NPC才解锁“成熟选项”，把人物交流写成标准答案奖励。
- **提前剧透**：中段立场说明直接说出后续账户、列名或反转。
- **回拨重复**：动态开场和下一段正文连续说同一遍。
- **未知被偷关**：NPC根据空备注、称呼或职业经验猜出身份和动机。
- **只测第一案**：全局测试通过，但被修改的第二、第三案从未在浏览器中打开。
- **状态门漏测**：材料板、立场快照、挂断、行动完成状态互相跳过或卡死。
- **用幕间代替结案**：上一案没有正式处置、下一案也没有开篇，玩家只看到两张材料卡硬接。
- **系统替玩家复盘**：用路线名、命中率或抽象比喻拼成旁白，既像AI，也泄露内部机制。
- **调查问题伪装成事实**：结案页把“是谁、为什么、能不能”这种问句当成未知结论。
- **一屏塞满问答**：问题、答案、操作和材料同时堆进一页，玩家既读不完也看不出下一步。

## 验证顺序

1. 运行内容索引与内容包校验。
2. 为新NPC动作、门控和回拨开场添加纯逻辑测试。
3. 运行完整逻辑与叙事流测试。
4. 构建可玩版本。
5. 用浏览器直接进入被修改的案件，不得只重跑第一案。
6. 实际走通：挂断前材料 → 立场快照 → 挂断 → 白天场景 → NPC动作 → 返回 → 第二夜开场。
7. 至少再走一条不同NPC选择，或用纯逻辑测试证明两条开场互斥。
8. 若修改共享运行时，重跑已完成案件的回归路线。

重点检查状态门：

- 场后材料结束后是否仍会进入应有的立场或挂断。
- 选择型NPC是否先显示回应，再允许离开。
- 普通幕间行动完成后是否清空活动页并返回调查台。
- 达到最少行动数后是否出现第二夜入口。
- 携带物和选择ID是否只解锁对应开场。

项目标准命令：

```bash
npm run content:index
npm run verify:pack
npm run test:logic
npm run test:narrative
npm run check
npm run smoke:browser
```

## 完成标准

只有同时满足以下条件才能报告完成：

- 有一版连续完整剧情。
- 有逐幕分镜和时长。
- NPC拥有欲望、方法、偏见、拒绝和真实地点。
- 白天选择改变第二夜。
- 真相边界与未知仍公平。
- 被修改案件已在浏览器实际走到第二夜或收麦。
- 共享流程的回归路线通过。

最终回复只报告：改了哪段故事、NPC如何改变、玩家新增了什么动作、修复了什么流程、跑了哪些验证。不要用“已优化”代替具体结果。
