# Case Scriptwriting

先读 [当前项目方向](references/current-project-direction.md)。这是项目创作约定的唯一维护入口；本 skill 负责怎样把它写进对白。用户当次要求优先，旧评审、小样和历史台词不自动成为新案的事实或硬性模板。来电人提出不讲理的要求时，先读 [无赖来电：谎盖谎](references/caller-shameless-demand.md)。谎盖谎主链、未改项清单和两连问已接入。还在打架的顺序、过满推断和作文腔，按 [逻辑与口语收口 Prompt](references/logic-and-spoken-voice-prompt.md) 改。

## 按改动范围工作

局部修句先读完整相邻交换及实际播放字段；整案重排才重建时间线、人物知识和场景顺序。只审不改就交付定位与建议；用户已要求修改时直接接入，不再因流程文件重复索要批准。不要为一句台词重做整套台本、强行召集多角色评审或扩大到无关案件。

来源、金额或动机断线时，用 [audit-case-spine](../audit-case-spine/SKILL.md)；确需设计谜面和回收时，用 [detective-plot-coupling-review](../detective-plot-coupling-review/SKILL.md)。跨夜、NPC或舞台变化用 [story-dialogue-staging](../story-dialogue-staging/SKILL.md)。这些是按需工具，不是每次必须串行运行的七套审查。

## 先建立当前交流

读目标 JSON、相关人物卡与当前连续台本，确认：
- 谁在说话，跟主播什么关系，现在要对方做什么。
- 到此处，玩家、主播和来电人各知道什么；信息从谁、哪份材料来。
- 上一句已经回答或拒绝了什么，下一句为什么接在这里。
- 新消息或人物出现的原因，以及它实际改变的事。

人物可以重复、答偏、反问、装懂和讲歪理。听众能跟上他在保护什么即可；不要求逐句复述上一句的关键词，也不要求每句交付新事实。主语不明、来源凭空出现、引用说错、突然回答另一件事，才需要补接话或重排。

## 写人物攻防

主播有经验、好奇心和脾气，可以顺着对方的理由聊几句，让她为证明自己有理而多讲，再抓她自己补出的不一致。也可以直接追问、阴阳或短暂误会。发现不对以后，对质里可以两连问：先钉已经露出来的错，再问一层显而易见能推出来的可能性，逼对方沉默或反驳；这仍是同一层，不是另开秘密。两连问写在 `lines` 的 host，不要写进 `entryQuestion` / `question` / `hostLine`。不要固定为“共情—核实—判断—补边界”。

来电人被发现问题后继续维护原诉求。她可以承认已经藏不住的事实，再争用途、争承诺、怪别人、挑词或挂断；不要替主播总结自己的动机，也不要为了凑多层伪装让她反复否认已经认过的事。对方给出成立的解释时，主播应调整判断。

用户指定的台词要结合已披露事实放到相应位置，不把示例里的事实擅自加进别案。讽刺、照顾、打岔和寒暄按人物关系使用，不设置每案数量和固定位置。

## 作者事实与人物表达分开

作者记录保留真实时间、金额、归属、合同关系、已知未知与来源范围。人物可以猜测、虚张声势或说错，但材料、旁白和系统不能把这句话直接认证为事实。主播有可见的怀疑依据就能问，不必先取得足以定论的文书；单纯紧张或拒答也不能证明一个外部事实。

- 不把相邻转账自动串为同一笔钱，不把历史消费当现有余额，不把返费规则当已入账回执。
- 不把第三方拒答改成主播代述的证词，不把公共事件倒推为个案的损失金额或责任。
- 已经披露设备属于谁，后面追用途或付款方式；不能再次指控她没说归属。
- 角色说“你刚才说……”时核对原话。尾声用引号复述时也要能追到已播原句；意思相近只能自然转述。
- 揭露不以招认作完成条件，真实照顾也不因后续欺骗被抹掉。不要为对称灰区给受害者编造过错。

内部来源限制服务作者核对，不能逐条搬到对白、材料旁边和片尾。必要的未知只说具体缺什么，不用免责声明撤回已经成立的判断。

## 按真实播放顺序接入

字段与存档细节见 [运行时内容接入](references/runtime-content-integration.md)。优先查看现有消费者，而不是把历史字段模板当成执行顺序。

多人对白以实际播放的 `lines` 为准；兼容 `answer` 同步来电人的回答，不用备用字段藏另一套解释。改一句时同时检查前后回答、`sceneCloser`、回拨开头、`hostDisclosure`、收麦和尾声引用。

主案与来电快案按当前方向集中问询，本段问清再推进；问错留在本段，不回到逐句回放或结尾刷完成度。其余案件仍有旧实现，改稿时同步迁移，不作为创作规范保留。`questionSequence` 只记录必要的事实先后，不要求扩写复杂因果链。口播快案任一有效点评推进。退款、发送、静音等动作发生后，后文不得又当成没做。

材料与当前问询同页核对，取消试问／正式出示双入口和强制多步配对。必要状态可以显示；单项推进不得标作“关键选择”，不用关键标识替玩家判断，来源索引、路线轴、正确答案推导不能作为玩家提示。

## 审读与验证

按实际路径读改动前后的完整段落，检查讽刺是否有指向、反驳是否接话、场尾是否提前知道后文、NPC是否重复首次寒暄。使用 [对白审读流程](references/story-review-workflow.md) 记录需要复验的具体接缝；[口语对照](references/spoken-corpus-patterns.md) 只提供候选形状，不作禁词或逗号配额。

内容接入后运行 `npm run content:index`、`npm run content:script` 和 `npm run check`。改变选项、顺序、材料或存档时重建 playable 并跑受影响浏览器路线。生成稿不能手改。

测试应验证来源、稳定 ID、动作顺序、进度恢复与呈现一致。除用户明确锁定台词外，不靠整句匹配或 skill 中的口号锁住文风。测试要求旧分支、认错、强制边界口播时，修正测试及对应规则，不把旧文案写回来。语义审读和实际试玩覆盖要分别报告。
