# 白话审读与接入流程

规则以 [当前项目方向](current-project-direction.md) 为准。本文件是执行方法，不是另一套创作法条。

## 1. 确认任务和来源

区分只审查、只记录、小样和接入修改；用户已经要求修改时继续做完，不重复请求确认。局部问题只读相关段落，整案重排检查必要的来源、问答与行动顺序，不为填表扩写复杂因果链。

读取实际内容 JSON、相关人物卡、当前生成稿和消费者。历史审稿意见不是已改入正文的证明，助手小样不是用户已接受的事实。记录原句、稳定 ID、前后交换和实际路线，避免沿旧数组下标改错说话人。

## 2. 先按当前动作串读

核对：当前请求、已回答或已执行的事、还在争什么、下一句从哪里来。

- “你刚才说”是否忠于原话，有没有擅加“只有、全部、一定”。
- 已经认过的归属、金额或动作是否再次作为初次秘密。
- 新人物、文件和消息是否有出现原因，而非作者需要它就来了。
- 回答是否在争词、维护利益或接梗；能听懂答偏就不必补解释。
- 退款、发送、静音、拒绝后的下一项是否承认已执行状态。
- 熟人首次寒暄是否保留，后续是否又重复自我介绍。
- 删除一句以后，后两轮是否还在回应旧稿。

人物可以反复、说错、突然惦记别的事；看完整小段是否能跟随，不把每句话变成有标准答案的问题。

## 3. 事实与追问

作者已知、玩家已见与角色知道的内容分别核对。内部表记录来源、范围和未知；不用角色把这张表念出来。

### 3A. 假设驱动的施压：直播不是法庭

有实际异常就能问可能的隐藏路线。主播不必等材料齐全，也不能先编一个人名、金额或因果再要求对方否认。判断变化应来自具体说辞、动作或材料，语塞和拒答不单独证明外部事实。

来电人为了保住诉求，可以改说法、缩小承诺、怪别人或挂断。揭露不要求认错和完整供述；对方解释成立时主播也要调整，不让所有问话必然命中。

### 3B. 主播的经验要体现在下一问里

问答涉及同一件事即可，不强制回声式复述。可以顺着她的得意、委屈聊几句，让她主动多讲；也可以抓住新细节直接问。不要每次点破后补责任划分与免责结论。

### 3C. 追着诉求问，让判断引出反弹

主播的讽刺要有当前事实，来电人的反驳要有维护对象；承认一个事实之后仍可争用途或责任。顺着聊、直问、打断、笑场都按场面选，不能再形成固定的共情—核实—训话模板。

收麦停在眼前最大问题或动作即可。片尾用户锁定字幕按当前项目方向保留，案内不因此扩展价值宣讲。

## 4. 按真实路径接入

见 [运行时内容接入](runtime-content-integration.md)。当前顺序中的下一问可以使用前一步必经回答，但不能使用可跳过材料或未来答案。旧分支转序列先消除互斥事实，不能仅修改 correct 字段后把旧结果依次拼上。

同步 `lines`、备用 `answer`、`sceneCloser`、回拨、现场反应、最终引用与人物知识。来源或授权记录放内部字段，玩家可见提示只显示必要出处和操作状态。

## 5. 验证与记录

构建索引及台本后运行当前检查；涉及顺序或存档时测试中间步骤保存、重载、继续与历史回放，涉及 UI 时看真实尺寸和截图。定点加载只证明该状态，不证明整条路径可达。

记录问题类型、具体源 ID、原文、改动、保留原因和实测覆盖。测试不能固定 skill 原句、句长、说辞层数或强制认错；保留稳定 ID、来源、顺序、进度恢复与呈现验证。

反复出现的问题追到共同原因，再修规则或消费者。不要把每次用户批注直接升级成全局禁词、全局结构或每段必须补的句型。
